# 記事描画エンジン 用語集

本書は記事描画エンジンで使う語彙の**唯一の定義元**とする。判断の経緯は[ADR](./adr/)を参照する。用語は日本語を正とし、英語は型・モジュール名などに使う。

## 分類

- **処理責務**：入力を別の文書表現や表示結果へ変換する仕事。実行するプロセス・言語・パッケージとは別の概念。
- **文書表現**：処理責務の入出力となるデータの意味上の段階。通信形式とは別の概念。
- **データ形式**：文書表現を保存・転送する際の符号化（Markdown、JSONなど）。
- **実行場所**：生成側（Astroのビルド、CLIの実行プロセス、チャットのバックエンドなど）と表示側（Web・ネイティブアプリなど）。「生成側」は常駐サーバーを意味しない。

## 処理責務

| 日本語 | 英語・コード上の呼称 | 定義 |
|---|---|---|
| **構造化** | Structuring / `structure` | 厳格Markdownソースの解析、構文・意味の検査、正規形への整形、意味ノードとIDの確定を行い、構造化文書を作る。 |
| **描画準備** | Preparation / `prepare` | 構造化文書に描画に必要な情報を付与する。カードの取得結果、コードの構文トークン、メディアの参照・埋め込みなどを確定し、描画用文書を作る。 |
| **描画** | Rendering / `render` | 描画用文書をHTMLやネイティブUIなど、表示環境に応じた成果物へ変換する。CSS適用や端末固有の操作はこの側の責務。 |

「描画準備」は**外部通信そのものを意味しない**。外部取得は環境側のアダプターが担い、取得結果の解釈と描画用文書への反映はPreparationが担う。取得失敗時も、代替表現を備えた描画用文書を作れる。

## 文書表現・成果物

| 日本語 | 英語・型名の候補 | 定義 |
|---|---|---|
| **厳格Markdownソース** | Strict Markdown Source / `SourceDocument` | 定められたMarkdown＋ディレクティブ記法で書くテキスト。形式上はMDX/JSXではない。 |
| **構造化文書** | Structured Document / `Segment`の列・`StructuredDocument` | 構文と意味が確定した型付きの文書モデル。参照先の取得情報やハイライトの色はまだ必要としない。 |
| **描画用文書** | Render-ready Document / `RenderSegment`の列 | 描画に必要な情報を用意し、HTMLとネイティブの両方が解釈できる型付き文書モデル。 |
| **描画結果** | Rendered Output | HTML文字列、静的ページ、ネイティブUIなどの描画成果物。 |

構造化文書と描画用文書は、どちらもセグメントの列として運ぶ。

| 日本語 | 英語・型名 | 定義 |
|---|---|---|
| **セグメント** | Segment / `Segment`・`RenderSegment` | 文書の直下にある要素1つ（見出し・段落・リスト全体・表・コード・ディレクティブ・前付けなど）を単位とする文書の区切り。規約の判定、確定、描画準備はこの単位で行う。 |
| **確定** | Confirmed | 後から届く入力でセグメントの中身と参照IDが変わらなくなった状態。途中入力では、改行まで届いた行のうち最後の要素より前が確定する。 |
| **拒否されたセグメント** | Rejected Segment / `RejectedSegment` | 規約に反したセグメント。原文と診断を持ち、他のセグメントの受け入れには影響しない。 |
| **カーソル** | Cursor / `Cursor` | 確定した位置と参照IDの番号の続き。呼び出し側が保持して次の呼び出しへ渡し、コアは状態を持たない。 |

`ResolvedDocument`（解決済み文書）、`部品（構造）`、`部品（解決済み）`は旧称として扱い、新しい仕様では使わない。JSONは「描画用文書」の別名ではない。型付きのデータをプロセス外へ渡す際、**必要に応じてJSONへシリアライズ**する。

## モジュール・境界

| 呼称 | 定義 |
|---|---|
| **Core（中核）** | 構造化と共通文書モデルの契約を所有する部分。入力の意味・正当性を確定する。HTTP、ファイルI/O、CSS、HTML・ブラウザAPIには依存しない。 |
| **Preparation（描画準備モジュール）** | 描画用文書を作る部分。取得処理の実行場所に依存せず、外部取得機能をアダプター経由で利用できる。Coreには含めない。 |
| **Renderer（描画器）** | 描画用文書を入力とする表示環境ごとの実装。HTML Rendererと各ネイティブRendererは別の実装になり得る。Coreには含めない。 |
| **Adapter（アダプター）** | ファイル・ネットワーク取得、Astro、CLI、アプリなど実行環境との接続を担う部分。 |
| **Theme（テーマ）** | 本文のHTMLのclassと属性へ当てるスタイル。Yomiloは最小テーマのCSSだけを配り、役割の名前と値の契約は利用側の表示層が持つ。 |
| **文書モデル** | 構造化文書と描画用文書の型・ノード集合・バージョン付きの公開契約。Markdownパーサーの内部ASTとは区別する。 |

## 入力規則と状態

- **記法（構文）**：許可するMarkdown／ディレクティブの形。エンジン共通の仕様。
- **正規形**：一つの意味に対して採用する、一意な厳格Markdownソースの書き方。`parse → format`の安定性を求める。
- **検査方針**：利用側が指定する必須属性・文書構成・配信制約など。記事公開と短いチャットメッセージで異なってよい。構文そのものを環境ごとに増やすことはしない。
- **完全入力**：閉じた構文と整った文書が揃った入力。公開記事・CLIの通常の検証対象。
- **途中入力**：生成中でコードフェンスやディレクティブなどが未完了の入力。確定したセグメントだけを返し、未確定の末尾は判定しない。
- **未対応部品**：文書モデルの許可集合にない要素。黙って捨てず、そのセグメントを診断付きで拒否する。

## 文書としての約束

「生成側が構造化・描画準備を担当し、表示側が描画を担当する」は**初期提供時の配置方針**であり、Core/Preparation/Rendererの論理的な責務境界を変更しない。Webの静的サイトやCLIは生成側で描画まで完了してよい。クライアント単独で構造化・描画準備を行う機能は、実際の需要が生まれてから検討する。
